IDプロバイダー マニュアル

はじめに

IDプロバイダーを使用することで、LDAP、Active Directory、OAuth2/OpenID Connectなどの 外部ディレクトリサービスを通じてユーザー認証を行うことができます。

対応プロバイダーの種類：

  • LDAP - 標準軽量ディレクトリアクセスプロトコル
  • Active Directory - Microsoft Active Directory
  • OAuth2 - OAuth 2.0 認可フレームワーク
  • OpenID Connect - OAuth 2.0 上のIDレイヤー

クライアントインポート

「クライアントインポートに使用」を有効にした場合、以下のデータがインポートされます：

  • 氏名 - sn（姓）または displayName
  • 名前 - givenName
  • 役職 - title（役職名）
  • 会社 - company
  • 住所 - street/streetAddress、postalCode、l（市区町村）、st（都道府県）、c（国）
  • 性別 - Active Directoryの場合、personalTitle（Herr/Frau）から取得

注意：OpenLDAPの場合、性別はデフォルトで「ニュートラル」となり、手動で修正できます。

ディレクトリ経由のサインイン

「認証に使用」を有効にして保存すると、ユーザーはディレクトリのパスワードで Klacks にサインインできます。 アクセス権が自動的に付与されることはありません。管理者が サインイン承認タブで一人ひとりを承認します。

  • このタブにはディレクトリアカウントが一覧表示されます（最大1000件。検索で一覧を絞り込めます）。
  • アカウントにチェックを入れると、ロールもパスワードもない新しい Klacks アカウントが作成されます。既存の Klacks アカウントが引き継がれることはありません。メールアドレスがすでに Klacks アカウントで使用されている場合、 その行にはチェックを入れられません。先にそのアカウントを削除するか、ユーザー管理でそのメールアドレスを変更してください。
  • チェックを外すと Klacks アカウントが無効になります。再度チェックを入れると、ロールがない限り再び有効になります。 ロールが残っている無効なアカウントは、ユーザー管理で再度有効にします。
  • 退職時の対応：誰かが退職したら、Klacks でもチェックを外してください。ディレクトリ側でアカウントを無効にすると 新しいサインインはブロックされますが、すでに実行中のセッションは有効期限が切れるまで継続します。
  • ディレクトリにメールアドレスがないアカウントは承認できません。
  • 自分自身のアカウントはこのタブで変更できません。
  • ディレクトリの認証情報が正しくても承認されていないユーザーには、アカウントが承認されていないため 管理者に連絡するようにというメッセージが表示されます。

Klacks はバインドユーザーで該当ユーザーを検索し、その後ディレクトリに対してパスワードを確認します。 そのため、ログイン名がメールアドレスと一致している必要はありません。

暗号化

ポート389のプレーンLDAPはパスワードを暗号化せずに送信します。SSLなしのLDAPプロバイダーでは、フォームに警告が表示されます。 ディレクトリをサインインに使用する場合は、必ずLDAPS（「SSLを使用」、ポート636）を使用してください。

Active Directory：サインインはLDAPSのみ

Klacks が Active Directory でユーザーをサインインさせるのは、LDAPS（ポート636）経由の場合のみです。SSLがない場合、フォームに警告が表示され、 誰もサインインできず、サインイン承認タブは閉じたままになります。SSLがない場合、クライアントインポートと接続テストが 動作するのは、Klacks が Windows 上で直接実行されている場合のみです。Docker（Linux）では、Active Directory のすべての操作に LDAPS が必要です。

  • ホスト：ドメインコントローラーの証明書に記載されているとおりの完全修飾名（FQDN） （例：dc01.example.local）。証明書の検証では名前が比較されるため、IPアドレスは使用できません。
  • CAを信頼する：Klacks を実行するコンピューターは、ドメインコントローラーの証明書を発行した認証局を 信頼している必要があります。Windows：CA証明書をコンピューターの 信頼されたルート証明機関 (Trusted Root Certification Authorities) ストアにインポートします（例：certutil -addstore Root ca.cer、 管理者として実行）。
  • 名前解決：FQDN をDNSで解決できない場合は、hosts エントリを追加します （Windows：C:\Windows\System32\drivers\etc\hosts）。
  • Docker：CA証明書をPEMファイルとしてAPIコンテナーにマウントし、 環境変数 LDAPTLS_CACERT にそのパスを設定します。DNSで解決できない場合は、 extra_hosts で FQDN を追加します。ドメインコントローラーがCA証明書を送信しない場合 （自己署名証明書）は、その証明書自体をPEMファイルとして使用すれば、信頼の基点として機能します。 信頼された証明書がない場合、接続は拒否され、接続エラーとして報告されます。
  • バインドアカウント：ユーザープリンシパル名（UPN）で入力します （例：svc-klacks@example.local）。

インポートされるアカウント

  • 無効なアカウントと Active Directory のシステムアカウントは、インポートも一覧表示もされません。
  • ユーザーフィルターでサービスアカウントを除外します（例：特定のグループのメンバーのみ）： (&(objectCategory=person)(objectClass=user)(memberOf=CN=Klacks,OU=Groups,DC=example,DC=local))

ヒント

Synology NAS を LDAPサーバーとして使用

Synology NASをLDAPサーバーとして使用できます。その場合、「LDAPサーバー」パッケージ またはOpenLDAPを使用したDockerコンテナーをインストールする必要があります。

  • プロバイダータイプ：「LDAP」（「Active Directory」ではありません）
  • ユーザーフィルター：(objectClass=inetOrgPerson)
  • ユーザーは uid またはメールアドレスでサインインします
  • LDAPS（ポート636）を推奨

接続のテスト

「接続テスト」ボタンを使用して設定を確認してください。ユーザーフィルターで見つかった有効なアカウントの数 （無効なアカウントとシステムアカウントは数えられません）と、いくつかのサンプルユーザー名が表示されます。 数の後ろの「+」は、ディレクトリサーバーが結果の上限で停止したことを意味し、さらにアカウントが存在します。
