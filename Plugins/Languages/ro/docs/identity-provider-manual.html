Manual Furnizor de Identitate

Introducere

Furnizorii de identitate permit autentificarea utilizatorilor prin servicii de directoare externe precum LDAP, Active Directory, OAuth2/OpenID Connect.

Tipuri de furnizori acceptate:

  • LDAP - Protocol standard de acces la directoare
  • Active Directory - Microsoft Active Directory
  • OAuth2 - Cadru de autorizare OAuth 2.0
  • OpenID Connect - Strat de identitate peste OAuth 2.0

Import clienți

Când „Utilizare pentru import clienți" este activat, următoarele date sunt importate:

  • Nume - sn (nume de familie) sau displayName
  • Prenume - givenName
  • Titlu - title (funcție)
  • Companie - company
  • Adresă - street/streetAddress, postalCode, l (localitate), st (județ), c (țară)
  • Gen - Pentru Active Directory, din personalTitle (Herr/Frau)

Notă: Pentru OpenLDAP, genul implicit este „Neutru" și poate fi corectat manual.

Conectarea prin director

Când „Utilizare pentru autentificare" este activat și salvat, persoanele se pot conecta la Klacks cu parola lor din director. Nimeni nu primește acces automat: administratorul aprobă fiecare persoană în fila Aprobarea conectării.

  • Fila listează conturile din director (cel mult 1000; folosiți căutarea pentru a restrânge lista).
  • Bifarea unui cont creează un cont Klacks nou, fără rol și fără parolă. Conturile Klacks existente nu sunt preluate niciodată: dacă adresa de e-mail este deja folosită de un cont Klacks, rândul nu poate fi bifat. Ștergeți mai întâi acel cont sau schimbați adresa lui de e-mail în administrarea utilizatorilor.
  • Eliminarea bifei dezactivează contul Klacks; o nouă bifare îl reactivează, atât timp cât nu are niciun rol. Un cont dezactivat care are încă roluri se reactivează în administrarea utilizatorilor.
  • Plecarea angajaților: când cineva pleacă, eliminați bifa și în Klacks. Dezactivarea contului din director blochează conectările noi, dar sesiunile deja pornite continuă până expiră.
  • Un cont fără adresă de e-mail în director nu poate fi aprobat.
  • Propriul cont nu poate fi modificat în această filă.
  • O persoană cu date de autentificare corecte din director, dar fără aprobare, primește mesajul că contul nu este aprobat și că trebuie să contacteze administratorul.

Klacks caută persoana cu utilizatorul de legătură și apoi verifică parola în director, astfel că numele de conectare nu trebuie să coincidă cu adresa de e-mail.

Criptare

LDAP simplu pe portul 389 trimite parolele necriptat; formularul afișează un avertisment pentru un furnizor LDAP fără SSL. Folosiți LDAPS („Utilizare SSL", portul 636) ori de câte ori directorul este folosit pentru conectare.

Active Directory: conectare doar prin LDAPS

Klacks conectează persoanele la Active Directory doar prin LDAPS (portul 636). Fără SSL, formularul afișează un avertisment, nimeni nu se poate conecta, iar fila de aprobare a conectării rămâne închisă. Fără SSL, importul de clienți și testul de conexiune funcționează doar când Klacks rulează direct pe Windows; în Docker (Linux), Active Directory necesită LDAPS pentru toate funcțiile.

  • Gazdă: numele complet calificat (FQDN), exact cum apare în certificatul controlerului de domeniu, de exemplu dc01.example.local. O adresă IP nu funcționează, deoarece verificarea certificatului compară numele.
  • Încrederea în CA: computerul pe care rulează Klacks trebuie să aibă încredere în autoritatea de certificare care a emis certificatul controlerului de domeniu. Windows: importați certificatul CA în depozitul Trusted Root Certification Authorities al computerului, de exemplu certutil -addstore Root ca.cer (ca administrator).
  • Rezolvarea numelor: dacă FQDN-ul nu poate fi rezolvat prin DNS, adăugați o intrare în fișierul hosts (Windows: C:\Windows\System32\drivers\etc\hosts).
  • Docker: montați certificatul CA ca fișier PEM în containerul API, setați variabila de mediu LDAPTLS_CACERT la calea lui și adăugați FQDN-ul cu extra_hosts dacă DNS nu îl rezolvă. Dacă controlerul de domeniu nu trimite un certificat CA (certificat autosemnat), propriul certificat ca fișier PEM funcționează ca ancoră de încredere. Fără un certificat de încredere, conexiunea este refuzată și raportată ca eroare de conexiune.
  • Cont de legătură: introduceți-l ca nume principal de utilizator (UPN), de exemplu svc-klacks@example.local.

Ce conturi sunt importate

  • Conturile dezactivate și conturile de sistem Active Directory nu sunt niciodată importate și nici listate.
  • Excludeți conturile de serviciu cu filtrul de utilizatori, de exemplu doar membrii unui grup: (&(objectCategory=person)(objectClass=user)(memberOf=CN=Klacks,OU=Groups,DC=example,DC=local))

Sfaturi

Utilizarea Synology NAS ca server LDAP

Puteți utiliza un Synology NAS ca server LDAP. În acest caz, trebuie să instalați pachetul „LDAP Server" sau un container Docker cu OpenLDAP.

  • Tip furnizor: „LDAP" (nu „Active Directory")
  • Filtru utilizatori: (objectClass=inetOrgPerson)
  • Utilizatorii se conectează cu uid sau cu adresa de e-mail
  • Preferați LDAPS (portul 636)

Testarea conexiunii

Utilizați butonul „Testare conexiune" pentru a verifica configurarea. Se afișează numărul de conturi active pe care le găsește filtrul de utilizatori (conturile dezactivate și cele de sistem nu sunt numărate) și câteva exemple de nume de utilizatori. Un „+" după număr înseamnă că serverul de director s-a oprit la limita de rezultate, deci există mai multe conturi.
